# AGENTS.md — agent-harness

A repository that ships one reusable agent harness to **both Claude Code and Codex**.
This file is the **single source of truth**. For Claude Code, `CLAUDE.md` imports it.

## Three layers (the core design)

- **core/** — the tool-agnostic canonical source: Agent Skills (standard `SKILL.md`),
  self-improvement hooks (`core/hooks/`), shared scripts, the memory schema, the handoff format.
- **adapters** — packaging of core for each tool:
  - `plugins/harness/` = the Claude plugin (published through the root `.claude-plugin/marketplace.json`)
  - `plugins/codex/` = the Codex plugin, which bundles both skills and hooks
    (published through `.agents/plugins/marketplace.json`; its manifest carries
    `"skills": "./skills/"` and `"hooks": "./hooks/hooks.json"`)
- **opinion pack** (`project-template/`, docs) — personal or team workflow, commit rules,
  retrospective style, plus the **hook data** (`routes.json`, `reflection-rules.json`).
  This part is taste, so it is kept separate and adopted by choice.

## The self-improvement hook loop (engine = core, data = project)

What sets this harness apart from plain skills is the **self-improvement loop**:
project-memory-index (inject the list of shared memories at session start)
→ memory-search (inject relevant memories before an edit) → reflection (quality warnings after
an edit) → pr-merge-reflect (retrospective on merge) → `/memory-update` promotion.

- **Engines** (`core/hooks/`) are tool-agnostic and generic. They never hardcode *what* to
  inject or warn about. Generic engines — skills and hooks alike — belong in `core/`.
- **Data** lives in the project's `.claude/memory/`: `routes.json` (file and shell command →
  memory mapping), `reflection-rules.json` (regex quality rules), `reflect-skip.json`
  (retrospective PR exception rules). Without them the hooks quietly no-op (only the built-in
  TODO/FIXME check and the default retrospective skip rules remain).
  Example data lives in `project-template/.claude/memory/`.
- **Hooks ship in full to Claude and partially to Codex.** Both sides use `hooks/hooks.json`
  and `${CLAUDE_PLUGIN_ROOT}` — Codex sets that variable too, as a compatibility alias
  (measured on 0.145.0). Codex registers it from the manifest under the `"hooks"` key.
  Four hooks are bundled for Codex, but `pr-merge-reflect` is registered only for its
  SessionStart and PostToolUse detection/queueing stages. The UserPromptSubmit reminder and
  the automatic LLM retrospective stay unregistered until they are measured on a real install.
  See `docs/codex-hooks.md` for the detailed limits and porting status.
- The **automatic retrospective job** (`reflect.py` drafting through `claude -p`) is **off by
  default**. It is gated behind a `HARNESS_AUTO_REFLECT=1` opt-in so that merely installing
  the plugin never starts a background LLM job. The reminder is always on where it is
  registered — that is Claude's UserPromptSubmit hook; Codex does not register that event yet.
- Path conventions — **bundled scripts** stay inside the plugin: hooks on both adapters use
  `${CLAUDE_PLUGIN_ROOT}`, Claude skills call commands from `bin/` on PATH, and Codex skills
  use their own `scripts/` directory. **Project data** resolves from the project root, which
  differs from the plugin root. How the project root is obtained differs per tool:
  - **Claude**: read it from the `CLAUDE_PROJECT_DIR` environment variable.
  - **Codex**: there is no such variable (measured on 0.145.0), and the skills' path note moves
    the working directory into the skill folder, which sits in a plugin cache outside the user's
    repository. So the Codex-rendered skills resolve an explicit absolute project path **before
    any `cd`**, write it literally into every project-file path, and pass it as `--project-dir`.
  - **Hooks resolve it in code, not from the skill text.** `project_dir(data)` in
    `core/scripts/hook_io.py` tries `CLAUDE_PROJECT_DIR`, then the `cwd` field in the hook input
    payload (which is what Codex supplies), then the process working directory as a last resort.

## Build

`core/` is the canonical source; adapters are generated by **copying** (no symlinks — safer for
cross-platform use and external distribution).

```bash
./build.sh   # core/ → plugins/harness (Claude) + plugins/codex (Codex). Always run before committing.
```

## Distribution (asymmetric — state the difference plainly)

- **Claude**: `/plugin marketplace add foxyberry/agent-harness` → `/plugin install agent-harness@foxyberry`
- **Codex**: `codex plugin marketplace add foxyberry/agent-harness`, or locally `codex plugin marketplace add ./`. No separate installer: the official marketplace CLI handles install, update and cache.
- **Both**: copy `project-template/` into the project (the canonical AGENTS.md plus the `.claude/memory` template)

Installation differs per tool, but the **user-facing command names stay identical**: `/handoff-save`, `/handoff-load`, `/fw`, `/fw-both`, `/history`, `/feedback-review`, `/memory-update`.

**handoff vs fw vs fw-both**: `handoff-save/load` = the portable canonical record a human commits explicitly (works across machines). `fw` = the fallback that reconstructs state from session logs (Claude `.jsonl` / Codex rollout) even when nothing was saved (same machine, for switching tools). The rendered `fw` passes the **opposite tool** as the `--from` default, so the current session cannot select itself. `fw-both` = the variant that reads **both Claude and Codex logs at once** (`fw --from both`) — use it when work is scattered across tools and you want to resume from the combination. The rendered `fw-both` passes `--current <current tool>` (rendered per adapter as claude or codex at build time) so that only **the current tool's live session** is excluded (the other tool's latest log is the immediately preceding work, so it is kept). In all three, **the current git state wins**.

`history` is a read-only browsing layer that restores nothing. It lists and searches the Claude
and Codex logs and hands the selected log path to `fw --session`.

### Update and release practice

- Do not push ordinary users to update often. Keep local dogfooding separate from user-facing releases.
- When shipping a user-facing change, bump the version in `plugins/codex/.codex-plugin/plugin.json`
  and `plugins/harness/.claude-plugin/plugin.json` **together** (keep them equal; never ask users
  to refresh a cache while leaving the version unchanged).
- Codex currently has no `plugin update`, so the update instructions are: `marketplace upgrade`,
  then `remove`/`add` to pull a fresh cache.
- Verify local development with `./build.sh` → `codex plugin marketplace add ./` →
  `codex plugin remove/add agent-harness@foxyberry`.
- **Update instructions must also say "close your Codex sessions first."** When Codex installs a
  new version it deletes the old version's cache folder, and a running session keeps pointing at
  the deleted path, which breaks its shell commands (restarting fixes it; nothing is lost). Claude
  keeps old versions, so this does not apply there. Since 0.8.1 the hooks absorb this themselves,
  but sessions started on an earlier version are still affected → `docs/codex-hooks.md`.
- Keep only the short user install/update commands in the README; if the procedure grows long,
  split it into a `docs/release.md`.

## What belongs in this harness (2026-08-17)

The test for whether a new skill or tool goes here:

> **If it handles state the agent itself produced (session logs, memory, hooks), it stays here.
> If it only handles git and GitHub, it is a general-purpose tool and goes to a personal
> `~/.claude/skills/` or another repository.**

This harness has exactly two purposes — letting **work be picked back up** across sessions,
tools and machines, and letting the **lessons from merged work survive as memory**. Anything
that fits neither is out of scope no matter how useful it is.

It did overflow once. On 2026-08-17, five skills (`merge-cleanup`, `prettier-guard`,
`stale-scan`, `review-ledger`, `verify-regression`) were moved out to personal scope (#105).
Adding a third axis ("inspection") kept accumulating ordinary git work such as branch cleanup
and issue triage, and that work was consuming most of the repository's maintenance cost.
**Keep it to two axes.**

When a case looks borderline, move it out rather than carving an exception. One exception and
the line blurs again.

## Rules

- Change core → run `build.sh` → commit the regenerated adapter output together with it.
- Keep script references inside the adapter: hooks on both adapters use `${CLAUDE_PLUGIN_ROOT}`;
  Claude skills call commands such as `agent-handoff` from `bin/` on PATH; Codex skills use
  `scripts/` relative to their own skill directory.
  Never reach outside the adapter with `../`.
- Committed shared memory requires governance: `_pending → human approval → committed`.
  No sensitive information.
- **Memory tier — personal is the default.** This repository is **public**, so anything placed in
  `.claude/memory/` is published to the whole world. Promote to shared (committed) only when one
  of these holds:
  - **Codex needs it to change code in this repository** (this harness does not automatically
    load Claude auto-memory into Codex sessions; the files are readable, but nothing reloads them)
  - **It is useful to external users** of this harness

  Your own work habits, reporting style and mistake history go to the **personal tier**
  (`~/.claude/projects/.../memory/`). The shared tier requires a PR, a review and a merge, so use
  it only when the value exceeds that cost.
- Work that needs cross-review goes in this order: **first review in Claude Code → fact and
  execution cross-check in Codex**.
- Do not let external review results end as a local report; leave them as a comment on the target
  PR or issue. If they were recorded in another thread, link the original from the target body or
  a comment.
- **Write PR and issue titles and bodies in English.** English is the primary text; a Korean
  version is optional and, if included, goes below the English as a supplement.
