Design note · agent-harness

결정을 어디에 저장하고
어떻게 꺼낼까

정본은 markdown, 인덱스는 파생 — DB 를 언제·어떻게 얹을지에 대한 설계 원칙.

핵심은 “markdown 을 DB 로 바꾼다”가 아니라 “markdown 위에 DB 를 얹는다”는 것. 저장을 md 로 할지 db 로 할지는 유저가 정하고, 인덱스로 꺼내 쓰게 돕는 건 하네스가 한다.

원칙 — 정본 vs 파생 인덱스

이건 선택이 아니라 층이다. markdown 이 진실, DB 는 빠른 조회를 위한 투영. 이 구분을 안 박으면(비전 문서의 .project-knowledge/처럼 md·jsonl·embedding 을 섞어놓고 정본을 안 정하면) 나중에 방향이 흔들린다.

◆ source of truth

정본 = git 에 커밋된 markdown

  • decisions/·memory/. 사람이 검토·curate.
  • 버전 관리 + 툴·머신 안 가림 + repo 따라 이동.
  • DB 로 대체 못 함 — governance·이식성이 여기 달림.
⟳ derived index

DB = 재생성되는 조회용 캐시

  • markdown 에서 rebuild. 잃어도 git 에서 재생성.
  • git 밖에(gitignore). 커밋하지 않음.
  • 임베딩·그래프를 git 에 넣으면 충돌·churn 지옥.

세 층으로 잡으면 안 흔들린다

두 층이 아니라 세 층이다. 아래가 진실(bedrock), 위로 갈수록 파생.

하네스 ③ retrieval contract 검색 계약 — search(query, filters) → 근거 붙은 결과 backend 무관. 소비자(질문에 답하는 AI)는 store 가 md든 db든 같은 모양을 받는다.
▲ 같은 계약
하네스 ② derived index ⟳ 인덱스 — 키워드 + 선택적 임베딩 store 에서 재생성 가능한 조회용 색인. gitignore.
▲ rebuild from
유저 ① source of truth 저장 store — markdown in git (또는 db) 사람이 검토·curate 하는 진실. 무엇으로 저장할지는 유저 판단.
미묘하지만 핵심: “md냐 db냐”(store 축)와 “키워드냐 의미검색이냐”(index 축)는 독립이다. 의미검색용 임베딩은 store 위에 얹히는 index라, md 를 정본으로 둔 채로도 벡터 검색이 된다. 하네스가 소유하는 건 인덱스+계약이지 정본이 아니다.

어떤 DB 를, 언제

지금 / 곧

벡터 DB

결정이 수백~수천이면 glob/grep 으로 “DB 지연 풀었던 사례” 같은 의미 질문을 못 함. pgvector 하나면 됨 — md 를 청크·임베딩한 gitignore 인덱스. 가장 정당하고 빠른 다음 칸.

나중 / 조건부

그래프 DB

“이슈→커밋→클래스→feature” 다중 홉 질의가 실제로 나오고 느려질 때. [[링크]]로는 traversal 이 안 되니까. 단일 프로젝트면 한참 뒤.

org 규모

중앙 history DB

불가피해지는 건 규모가 아니라 범위 — 한 repo 가 아니라 수십 repo 가로질러 “우리 회사가 결제 지연을 어떻게 풀어왔나”를 물을 때. per-repo md 는 안 합쳐짐.

검색을 잘 되게 하는 법

가장 큰 함정은 “벡터만 쓰기” — 클래스명·이슈번호·API 경로 같은 정확한 토큰을 놓친다. 그래서 키워드+벡터 하이브리드가 기본. 레시피는 순서가 있다:

  1. 메타데이터로 먼저 좁힌다. frontmatter(chain·status·keywords·valid_from)로 “superseded 제외·feature=payment·그 시점 유효”를 필터 → 정밀도 급상승.
  2. 하이브리드로 후보를 뽑는다. 키워드(BM25) + 벡터를 각각 뽑아 RRF 로 융합.
  3. LLM 으로 top-k 재정렬. 후보 20개쯤을 “진짜 답하는 순서”로. 작은 코퍼스에선 특히 싸고 효과 큼.
  4. 근거를 붙여 반환한다. evidence(commit·PR·issue)·confidence·원본 md 포인터. 근거 못 대면 검색이 끝난 게 아니다.
임베딩은 원문 통째 말고 “검색 표면”을: description + keywords + 심볼명 + Context/Decision 요약. 그리고 측정 없이 못 맞춘다 — north-star 질문 20~30개를 질문→기대 근거 골든셋으로 만들어 recall@k 로 튜닝. 작으면 벡터도 아직 불필요 — 키워드+메타필터+LLM 재정렬로 시작.

하네스가 정의할 최소 계약

memory-search 훅 + INDEX.md 가 이미 “md store 위에서 검색해 주입”의 원시 버전이다. 이걸 store-agnostic 검색 엔진으로 승격시키는 것 — 정의할 건 두 개뿐:

// ① 검색 계약 (backend 무관)
search(query, filters) -> [{ id, text, evidence, confidence, source }]

// ② store 어댑터 인터페이스
//    md-backend (기본) 와 db-backend (opt-in) 가 둘 다 구현.
//    routes.json·reflection-rules.json 처럼 "데이터는 프로젝트가" 패턴의 store 판.
StoreAdapter { list(), read(id), rebuildIndex() }

즉 새 시스템이 아니라 memory-search 의 확장이다.

왜 이런 흐름이 없었나 (왜 지을 가치가 있나)

“아무도 안 한다”가 아니라 이제야 태어나는 중 + 원래 하기 싫은 종류라서다. 그래서 방어 가능한 자리이기도 하다.

01
데이터를 도구가 못 만든다

가치는 “왜”가 적혀 있을 때만. 근데 안 적는 게 습관 → 품질 천장이 사용자의 최악의 습관에 묶임. ADR 이 안 퍼진 이유.

02
비용은 지금, 이득은 나중에·남에게

아는 사람이 비용, 6개월 뒤 다른 사람이 이득. 강제 장치 없으면 안 함. 문서·테스트가 썩는 병.

03
데모 되는 절반이 이겼다

구조·검색은 결정론적·평가가능·데모 예쁨. 의도·근거는 흐릿·recall 낮음. 업계가 구조를 지음.

04
뽑는 기술이 이제 막 됐다

PR 토론→의도 요약을 쓸 만한 품질로 하게 된 게 최근. 없는 게 아니라 2025~26 태어나는 중.

아이러니: 당신은 이미 손으로 한다(nonresidential-unit-price-estimation.md). 가치는 증명됐고, 규율을 낮은 마찰 + 자동 초안 + 사람 검토 게이트로 바꿔주는 게 해자다.
so — 지금 할 일

DB 를 짓지 말고, 인덱스를 얹어라

“지금 DB 를 지어야 하나”의 답은 아직 아니다. 첫 DB 는 벡터 인덱스이며, 그것도 markdown 을 대체가 아니라 색인하는 형태 — pgvector, gitignore, north-star 로 평가. markdown 정본은 계속 유지. 그걸 버리는 순간 그냥 또 하나의 CodeScene 이 된다. 이 원칙만 박아두면 시스템이 커져도 방향이 안 흔들린다.
