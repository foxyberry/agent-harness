agent-harness

Claude Code + Codex에서 함께 쓰는 에이전트 도구묶음

"에이전트가 지난 실수에서 배울 수 있게 돕는 장치"를 한 프로젝트 안에만 두지 않고, 어느 프로젝트에서나 /plugin install 한 번으로 가져다 쓸 수 있게 만든 도구다. 작업 넘겨주기, 회고, 함께 보는 메모리, 자주 쓰는 작업 명령을 한 번에 설치한다.

왜 다른가 (차별점)

비슷한 도구들은 보통 작업이 끝날 때 기록을 남기는 것에서 멈춘다. 이 도구는 조금 더 이어서 도와준다:

  • 스스로 돌아보는 흐름 — 편집 전에 관련 메모리를 보여주고 → 편집 뒤에는 자주 나는 실수를 알려주고 → 머지할 때 회고를 남기고 → 사람이 확인한 뒤 공유 메모리로 올린다.
  • PR이 머지될 때 회고 — 대화가 끝나는 순간이 아니라, 실제 작업이 합쳐질 때 배운 점을 남긴다.
  • git으로 함께 보는 메모리 — 내 컴퓨터에만 있는 대화 기록 대신, git에 남는 메모리로 다른 머신·사람·툴이 이어받는다.
  • 사람 확인 절차 포함 — _pending → 사람 승인 → committed. 잘못 배운 내용이나 민감한 정보가 자동으로 들어가지 않게 막는다.
01
자가 개선

작업하는 동안 스스로 배우고, 다음엔 더 잘한다 — 편집 전 힌트 · 편집 후 점검 · 머지 후 회고

자기개선 루프

한 번 쓰고 끝이 아니라, 작업할 때마다 이 네 단계가 계속 돌면서 조금씩 똑똑해진다. 마지막 단계(④)에서 남긴 메모리가 다음 바퀴의 첫 단계(①)로 다시 쓰인다.

  • ①편집 전 — 이 파일에 필요한 규칙·결정을 미리 꺼내 보여준다
  • ②편집 후 — 방금 쓴 코드의 흔한 실수·미완성 흔적을 바로 알려준다
  • ③머지 시 — 이번 작업에서 배운 걸 회고하라고 알린다
  • ④승격 — 사람이 확인해 메모리로 남긴다 → 다음 바퀴 ①로 이어진다

③~④ 회고를 사람이 직접 하느냐, 뒷단에서 자동으로 하느냐는 옵션 하나로 갈린다:

옵션 꺼짐 기본값

머지되면 "회고하라"고 알림만 뜬다. 회고는 사람이 /memory-update로 직접.

옵션 켜짐 HARNESS_AUTO_REFLECT=1

머지될 때마다 뒷단에서 자동으로 대화를 돌아봐 회고 초안을 만들어 _pending/에 쌓아둔다. 사람은 검토만 하면 된다.

자동 훅 4개 (Claude용 묶음)

언제훅하는 일프로젝트 설정
세션 시작할 때project-memory-index이 프로젝트에 어떤 공유 메모리가 있는지 목록을 먼저 알려줌.claude/memory/INDEX.md
파일 고치기 직전memory-search파일에 맞는 메모리를 에이전트에게 미리 알려줌routes.json
파일 고친 직후reflection코드에서 자주 보이는 문제를 알려줌 (정규식 규칙 + 기본 TODO/FIXME 확인)reflection-rules.json
머지·세션시작·발화pr-merge-reflect아직 회고하지 않은 PR을 알려주고, 원하면 자동 회고 초안(교훈 + 결정 ADR)도 만듦env HARNESS_AUTO_REFLECT

project-memory-index는 루프의 단계라기보다 루프에 시동을 거는 쪽이다. 세션이 열리면 "이 프로젝트엔 이런 메모리가 있다"는 목록을 먼저 깔아두고, 그 뒤 파일을 열 때 memory-search가 그중 지금 필요한 본문을 꺼내 ①로 넘긴다.

"자동"이라는 말의 뜻 — 돌아가는 것과 말을 거는 것은 다르다

4개 모두 플러그인만 깔면 따로 켜지 않아도 해당 순간마다 실행된다. 여기까지는 무조건이다. 하지만 실행됐다고 항상 뭔가를 알려주는 건 아니다. 대부분은 프로젝트에 재료가 있을 때만 입을 연다 — 없으면 아무 말 없이 지나간다(고장이 아니다).

✅ 맨입에도 동작

아무 설정 없이 설치만 해도 바로 말을 건다

  • reflection — TODO·FIXME 확인은 내장이라 기본으로 켜져 있다
  • pr-merge-reflect — "회고 안 한 PR 있다"는 알림까지는 항상

🧾 재료가 있어야 동작

해당 파일이 없으면 조용히 지나간다

  • project-memory-index — .claude/memory/INDEX.md
  • memory-search — routes.json, 그리고 지금 여는 파일과 맞는 규칙이 있을 때
  • reflection의 프로젝트 규칙 — reflection-rules.json
  • 자동 회고 초안 생성 — HARNESS_AUTO_REFLECT=1
⚠️ 파일을 어떻게 고치느냐도 영향을 준다. memory-search와 reflection은 에이전트가 편집 도구로 파일을 고칠 때만 걸린다. 터미널 명령으로 파일을 바꾸면 (예: sed나 > 리다이렉션) 이 둘은 아예 실행되지 않는다.

project-template/를 복사하지 않은 새 프로젝트라면 4개 중 2개가 조용한 게 정상이다. 재료를 넣는 순간부터 말을 걸기 시작한다.

핵심 설계 — 엔진과 재료를 분리

도넛 기계와 반죽을 나눠 두었다고 보면 쉽다. 기계는 만드는 방법만 알고, 어떤 맛을 낼지는 각 프로젝트가 넣는 반죽이 정한다.

🛠 엔진 (core)

툴이나 프로젝트가 달라도 함께 쓰는 기본 부품. "무엇을" 보여주고 경고할지는 코드에 박아두지 않는다. 모든 프로젝트가 공유한다.

🧾 데이터 (프로젝트)

.claude/memory/의 routes.json·reflection-rules.json이 "우리 프로젝트에서는 이렇게 한다"를 정한다. 프로젝트마다 다를 수 있다.

전에는 기계 안에 "Kotlin 규칙"이 통째로 박혀 있었다. 이제 그 부분을 꺼내서 기계는 공통으로 쓰고, 프로젝트마다 필요한 재료를 넣도록 나눴다. Java든 Python이든 자기 프로젝트에 맞는 재료만 넣으면 같은 기계가 돈다. 설정이 없으면 훅은 아무 일도 하지 않고 조용히 지나간다.

⚠️ 자동 회고는 기본으로 꺼져 있다. 자동 회고 작업은 claude -p(AI)를 뒤에서 실행한다. 설치만 했는데 AI가 몰래 돌지 않도록, HARNESS_AUTO_REFLECT=1로 직접 켰을 때만 동작한다. 회고 알림은 이 설정과 상관없이 항상 켜져 있다.

돌고 있는지 어떻게 아나 (확인 방법)

훅이 조용해서 "정말 도는 건가?" 싶을 수 있다. 이건 고장이 아니라 의도한 방식이다. 대부분의 내용은 화면이 아니라 에이전트에게 직접 전달된다. 확인하려면 아래 위치를 보면 된다:

🙈 화면에 안 보이는 것 — 에이전트에게 전달

화면에는 뜨지 않고 에이전트가 참고할 내용으로 조용히 들어간다

  • memory-search — 파일을 열면 관련 메모리를 에이전트에게 전달
  • reflection — 방금 쓴 코드의 문제를 도구 결과 옆에 알려줌
  • 머지 리마인더 — "회고부터 하자"는 알림을 다음 대화에 보여줌

👀 직접 볼 수 있는 것 — 파일로 남음

디스크에 실제 파일이나 로그로 남아서 직접 확인할 수 있다

  • .claude/memory/*.json — 있으면 설치된 상태
  • _pending/*.md — 회고 초안 (/memory-update로 확인)
  • .cache/reflect.log — 회고 기록 (auto-reflect 켰을 때)
초안이 실제 파일로 쌓이는 걸 보고 싶다면 자동 회고를 켠다 — export HARNESS_AUTO_REFLECT=1. 그러면 PR이 머지될 때마다 _pending/에 회고 초안이 생긴다. (끄면 알림만 뜨고, 회고는 /memory-update로 직접 한다.)

자가개선 관련 명령

명령언제 쓰나하는 일
/feedback-review머지 후 · 회고 시받은 지적을 다음에 쓸 규칙이나 스킬로 남길지 검토
/memory-update머지 후 · 초안 쌓였을 때배운 것을 함께 보는 메모리로 저장 (_pending 확인·반영)

의사결정 기록 (ADR)

회고 루프는 "무엇을 배웠나"(교훈 메모리)뿐 아니라 "왜 그렇게 결정했나"도 남긴다. 코드는 "무엇을 했나"만 보여준다 — 6개월 뒤 사람 머릿속에서 증발하는 결정의 이유를 한 건씩 기록하는 게 ADR(Architecture Decision Record)이다.

⏩ 앞으로 — 회고가 초안

자동 회고가 교훈과 함께 결정 ADR 초안도 만들어 _pending/decisions/에 쌓는다. 결정끼리의 계보(체인)·대체 관계는 제안만 하고, 사람이 /memory-update로 확정한다 — 잘못 이어붙인 가짜 역사를 막기 위해서다.

⏪ 과거 — git에서 소급

mine.py가 git 히스토리(커밋 메시지)에서 이미 내린 결정을 뽑아 같은 ADR 초안으로 떨군다. 커밋에 "왜"가 안 적혀 있으면 초안을 만들지 않도록 지시하며, 생성된 초안은 사람이 검토한다.

둘 다 같은 승격 경로를 탄다 — _pending/decisions/ → 사람이 /memory-update로 확정 → .claude/memory/decisions/. 과거는 마이닝으로 씨앗을 깔고, 이후는 회고로 이어 붙여 하나의 결정 계보가 된다.

ADR 게이트: 본문에 Alternatives(안 고른 대안)와 Consequence(결과)가 둘 다 있어야 ADR로 인정한다. 둘 중 하나라도 없으면 /memory-update 검토에서 ADR로 승격하지 않고, 일반 메모리로 돌리거나 폐기한다 — 아무 선택이나 결정 기록으로 만들면 검색이 무너지기 때문이다.
02
Handoff

세션·머신·툴·사람이 바뀌어도 작업을 끊김 없이 이어받는다

핸드오프 명령

명령언제 쓰나하는 일
/handoff-save세션 끝 · 툴/머신/사람 바꾸기 직전다음 사람이 이어받기 쉽게 현재 상태를 커밋 파일로 저장 (git 정보 자동수집)
/handoff-load작업 이어받을 때커밋된 핸드오프를 읽고 현재 git 상태와 비교
/fw저장 안 하고 툴만 바꿨을 때반대 툴의 대화 기록에서 하던 일을 자동으로 복원 (같은 머신)
/fw-both여러 툴을 오가며 작업했을 때Claude·Codex 기록을 한 번에 보고 합쳐서 이어받음
/handoff-save와 /fw의 차이: 핸드오프는 사람이 일부러 저장해 git에 올리는 정식 방법이라 다른 머신·다른 사람에게도 넘어간다. /fw는 저장하는 걸 깜빡했을 때를 위한 보조 수단이라, 같은 컴퓨터에 남은 대화 기록을 뒤져 복원한다 — 그래서 다른 머신으로는 못 넘어간다. 셋 다 지금 git 상태를 먼저 믿고, 기록은 참고로만 쓴다.

핸드오프는 세션·툴·머신·사람이 바뀌어도 작업을 이어가기 위한 방법이다 — 흐름은 이렇다:

세션 A지금 작업 중 → /handoff-save "한 줄 요약"
▼  git commit · push  (.claude/handoff/<브랜치>.md — git 사실 자동수집)
세션 B다른 머신 · Codex · 동료가 /handoff-load 로 이어받음
왜 파일로 남기나: 내 컴퓨터에만 있는 대화 기록은 다른 사람이 읽기 어렵다. git에 커밋되는 핸드오프 파일은 clone/pull 하는 누구에게나 전달된다. 이 저장소 작업도 /handoff-load로 이어받아 시작했다.

무엇이 기록되나

이 도구가 남기는 건 전부 평범한 마크다운 파일이다 — 특별한 데이터베이스도, 특정 툴 전용 형식도 아니다. 그래서 git에 올라가고, 어느 머신·어느 툴에서나 그대로 열린다. 세 종류가 쌓인다:

📋 핸드오프 — .claude/handoff/<브랜치>.md

"지금 어디까지 했는지" 작업 상태. 브랜치·커밋·바뀐 파일 같은 git 사실은 자동으로 채워진다.

# 작업 핸드오프 — main
## 요약         이 작업이 뭐였는지 한두 줄
## 완료한 것     이미 끝낸 항목
## 남은 것       이어받는 사람이 바로 할 일
## 검증 상태     테스트·빌드 결과
## Git 사실(자동)  브랜치 · 커밋 · 바뀐 파일

🧠 공유 메모리 — .claude/memory/*.md

"앞으로도 기억할 규칙·결정". 사람이 확인해 올린 것만 여기 남는다.

---
name: engine-data-separation
description: 한 줄 설명 (목록에 표시됨)
type: feedback | project | reference
---
핵심 내용 + Why(왜 이렇게) · How to apply(어떻게 적용)

📝 회고 초안 — .claude/memory/_pending/*.md

자동 회고가 만든 후보. 메모리와 같은 형식이지만, 사람이 /memory-update로 확인하기 전까지는 여기서 대기한다(잘못된 내용이 바로 안 박히게).

메모리에 넣기 전 — 오래 남길 지식인지 먼저 구분

메모리는 계속 참고할 지식만 담는다. 지금 작업 상태까지 넣으면 PR·코드가 바뀐 뒤에도 오래된 내용이 남기 때문에, /memory-update가 저장 위치를 고르기 전에 수명부터 나눈다.

영속 지식

반복될 실수, 비자명한 패턴, 결정의 이유, 안정적인 계약

사람이 확인한 뒤 memory에 저장

전환용 작업 상태

WIP, 진행 중 PR, 다음 액션, 재개 체크포인트

실제로 세션·툴·머신·사람을 바꿀 때만 handoff를 제안

다시 구할 수 있는 값

줄 수, 테스트 수, 열린 PR 상태, 현재 브랜치·커밋

저장하지 않고 코드·git·명령으로 다시 확인

번호보다 상태가 문제다. PR #123은 결정의 근거를 가리키는 링크로 남길 수 있지만, PR #123 머지 대기는 곧 틀릴 수 있어 메모리에 남기지 않는다. _pending의 회고 초안도 같은 기준을 통과해야 공유 메모리로 승격된다.

다른 머신에서 이어받기

비결은 딱 하나 — 대화 기록은 두고, 커밋된 파일만 넘긴다. 무엇이 넘어가고 안 넘어가는지가 핵심이다:

❌ 안 넘어가는 것

내 컴퓨터·내 툴에만 있어 남이 못 읽는다

  • 대화 기록 (.jsonl) — 세션 로그, 로컬 전용
  • 임시 캐시 (.claude/.cache/)

✅ 넘어가는 것

git에 올라가 clone/pull 하면 어디서든

  • 핸드오프 (.claude/handoff/*.md)
  • 공유 메모리 (.claude/memory/*.md)

머신 A에서 /handoff-save → commit·push 하고, 머신 B에서 pull → /handoff-load 하면 저장된 상태를 읽고 지금 git과 대조한 뒤 그대로 이어받는다. 대화 기록이 없어도 되는 이유다.

다른 툴에서 쓰기 (Codex ↔ Claude Code)

같은 하네스를 Codex에서도 Claude Code에서도 쓸 수 있고, 서로 작업을 넘길 수도 있다. 되는 이유:

  • 파일 형식이 툴을 안 가린다 — 핸드오프·메모리 .md는 그냥 마크다운이라 Codex도 Claude도 똑같이 읽는다.
  • 명령 이름이 같다 — 설치 방법은 툴마다 달라도 /handoff-save·/memory-update 같은 이름은 양쪽 통일돼 있다.
  • 한 곳에서 관리 — 스킬은 core/에서 두 툴용 사본으로 자동 생성되니(build.sh), 고칠 땐 한 곳만 고치면 둘 다 바뀐다.
  • 회고도 양쪽을 이해 — 자동 회고는 Claude 대화 기록과 Codex 세션 기록을 둘 다 읽어 요약한다.
예: 낮에 Codex로 작업하다 /handoff-save → 커밋. 저녁에 Claude Code로 /handoff-load → Codex가 남긴 상태를 그대로 받아 계속. 툴이 바뀌어도 작업은 안 끊긴다.

정리 · 점검

사람이 반복하던 뒷정리를 대신 찾아준다 — 단, 실행은 사람이

정리·점검 명령 (전부 제안만 한다)

세 명령은 성격이 같다. 후보를 찾아서 보여주기만 하고, 스스로 지우거나 닫거나 고치지 않는다. 브랜치 삭제·이슈 닫기·파일 덮어쓰기처럼 되돌리기 번거로운 일이라, 마지막 판단은 사람이 하도록 남겨뒀다.

명령언제 쓰나찾아주는 것
/merge-cleanupPR 머지한 직후뒤처진 main, 남은 브랜치, 안 닫힌 이슈, worktree·임시파일 잔여물
squash merge의 로컬 브랜치·연결 worktree 판정은 이슈 #50에서 보완 예정
/stale-scan이슈 백로그 정리할 때오래 열려 있지만 이미 해결된 이슈 — 근거로 머지된 PR을 함께 보여줌
/prettier-guardprettier --write 돌리기 전남의 미완성 변경이 섞인 파일을 빼고, 안전한 명령을 대신 제안
/stale-scan은 근거의 세기까지 구분한다. 이슈에 딸린 PR이 Closes #33처럼 닫겠다고 선언한 것인지, 그냥 번호만 언급한 것인지 나눠서 표시하고, 선언이 있는 쪽을 위로 올린다. 언급뿐이라고 후보에서 빼지는 않는다 — 실제로 해결한 PR이 선언 없이 머지되는 경우도 있기 때문이다.

설치 · 구조

어떻게 깔고, 저장소가 어떻게 구성돼 있나

설치

Claude Code (플러그인으로 바로 설치):

/plugin marketplace add foxyberry/agent-harness
/plugin install agent-harness@foxyberry

Codex (현재는 스킬만 제공 — 설치 도구는 만드는 중):

codex plugin marketplace add git@github.com:foxyberry/agent-harness.git
codex plugin add agent-harness@foxyberry
# 또는 로컬: codex plugin marketplace add ./
⚠️ Codex는 지금 SSH 주소를 써야 한다. 이 저장소가 아직 비공개라서다. owner/repo 짧은 형식은 인증 없이 HTTPS로 받아오려 하기 때문에 비공개 상태에서는 실패한다 (실제로 Repository not found로 막히는 걸 확인했다). 저장소가 공개되면 짧은 형식을 쓸 수 있다. Claude 쪽은 짧은 형식 그대로 설치되는 것을 확인했다.

공통: 프로젝트에 project-template/를 복사한다 (AGENTS.md 기준 문서 + .claude/memory/ 예시 파일).

업데이트 — Codex에는 아직 plugin update가 없어서, 새 버전은 marketplace upgrade 뒤 remove·add로 캐시를 다시 받는다. 자주 할 필요는 없고, 새 릴리스가 나왔을 때만 하면 된다.

구조 (3층)

층위치내용
corecore/마스터 원고 — 스킬·훅·스크립트·메모리 형식이 여기서 시작
도구별 사본plugins/harness/, plugins/codex/각 도구에 맞게 포장된 사본 (build.sh로 자동 복사)
선택 템플릿project-template/개인/팀의 작업 방식과 회고 방식 (필요할 때 선택해서 사용)

core/는 마스터 원고이고, plugins/harness/와 plugins/codex/는 내보내기 버튼을 누르면 찍혀 나오는 사본이다. 고칠 때는 마스터 원고인 core/를 먼저 고치고 → ./build.sh를 눌러 내보내고 → 사본을 다시 만든다. 사본을 직접 고치면 다음 내보내기 때 덮어써진다.

core/마스터 원고 — 훅 · 스킬 · 스크립트 · 메모리 형식 (여기서만 고친다)
▼  ./build.sh 가 복사·렌더 (심링크 X — 크로스플랫폼 안전)
plugins/harness/Claude용 사본 · 스킬 9개 + 훅 hooks.json 자동발견
plugins/codex/Codex용 사본 · 스킬 9개 (훅은 나중에)
▼  /plugin install · marketplace
사용자 프로젝트project-template/ 복사 → .claude/memory/ 데이터(엔진의 재료)

core/ 한 곳을 고치면 두 사본이 함께 만들어진다. CI가 "마스터 원고와 사본이 같은지" 확인하므로, build.sh를 안 돌린 채 커밋하면 실패한다. JSON·스크립트 문법 검사와 tests/의 단위 테스트도 CI에서 매번 함께 돈다.
