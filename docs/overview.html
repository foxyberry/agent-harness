agent-harness

A shared toolkit for Claude Code + Codex

Carry work across sessions, tools, machines, and people, and keep lessons available for the next task. Install the harness through each tool's marketplace to get handoff skills, retrospective workflows, and hooks that surface project memory while you work.

New here? Start with the usage guide to choose a command by situation. This page explains the design and implementation, based on release 0.12.2 (reviewed 2026-09-15).

What the harness connects

  • A learning loop — surface relevant memory before an edit, warn about recurring problems afterward, prompt for a retrospective after a merge, and promote lessons after human review.
  • Retrospectives tied to PR merges — capture lessons when work lands, rather than only when a conversation ends.
  • Memory shared through git — committed knowledge can reach another machine, person, or tool.
  • Human approval — _pending → human approval → committed keeps unreviewed lessons and private draft material out of shared memory.
01
Self-improvement

Hints before edits, checks afterward, and lessons from merged work

The self-improvement loop

Memory approved in step ④ becomes input for step ① on a later task. These are workflow steps, not a guarantee of automatic learning: warnings use configured patterns, retrospective drafting is optional, and promotion always requires human review.

  • ①Before an edit — surface relevant rules and decisions.
  • ②After an edit — flag configured patterns and TODO/FIXME markers.
  • ③After a merge — Claude reminds you to review lessons; Codex currently detects and queues the PR.
  • ④Promotion — a human approves memory for the next cycle.

In the Claude adapter, one option enables background drafting. It never removes the human approval step:

Automatic drafting off DEFAULT

Eligible merged PRs trigger a reminder. Use /feedback-review to review lessons and /memory-update to persist them.

Automatic drafting on HARNESS_AUTO_REFLECT=1

Eligible merge events can start a background LLM job that writes drafts to _pending/ for human review.

Both adapters bundle four hooks. Codex registers pr-merge-reflect only for SessionStart and PostToolUse detection and shared queue updates. UserPromptSubmit reminders are deferred, and the Codex package does not bundle the automatic LLM job. See Codex hook constraints.

Automatic execution and visible output are different

Claude registers all four hooks for their supported events. Codex hooks run only after you trust them. A running hook often produces no output: most checks need project data and a matching event.

✅ Built-in behavior

Available without custom rules, when the relevant event and prerequisites are present

  • reflection — TODO/FIXME checks are built in.
  • pr-merge-reflect — detects eligible PRs; Claude reminders do not require automatic drafting to be enabled.

🧾 Needs project input

Missing input means the corresponding behavior stays quiet

  • project-memory-index — .claude/memory/INDEX.md.
  • memory-search — routes.json and a matching path or command rule.
  • reflection project rules — reflection-rules.json.
  • Automatic drafting — Claude adapter, HARNESS_AUTO_REFLECT=1, and its runtime dependencies.
⚠️ How you edit matters. File-based memory routing and post-edit warnings depend on supported edit events. A shell command that changes a file does not automatically become a file edit event. memory-search can still match that shell command through command routes; reflection does not inspect shell-written files.

Without project memory data, the index and routing hooks normally stay quiet. Copy and adapt the relevant files from project-template/ to configure them.

Core design — separate engine from data

The engine defines how to match and inject information. Each project supplies what to match and what to say.

🛠 Engine (core)

Reusable components shared across tools and projects. Project-specific rules are not hardcoded into the engine.

🧾 Data (project)

.claude/memory/ contains routes.json, reflection-rules.json, and other configuration that defines local behavior.

The engine once embedded Kotlin-specific rules. Those rules now belong to project data, so the same engine can serve Java, Python, or another project. Missing configuration disables the corresponding custom behavior; built-in checks and default retrospective skip rules remain.

Project input crosses a trust boundary

Configuration and the files it references come from the open repository. Hooks place that material into the agent's context, so the engine treats it as repository-provided reference data:

  • Bounded total injection — the budget covers the combined content and file names.
  • Empty patterns are ignored — they would otherwise match everything.
  • Source labels identify injected text as repository reference material, not instructions.
  • Local exclusions for _pending/ and _rejected.md are maintained by the engine in .git/info/exclude, independent of the optional template. Exclusions do not untrack files already committed.
⚠️ Automatic retrospectives are off by default. In the Claude adapter, the job invokes claude -p by default and starts only after you opt in with HARNESS_AUTO_REFLECT=1. Claude reminders are independent of that setting. Setting it in Codex does not enable the deferred drafting stage.

How to tell whether it is running

Many hook messages enter the agent's context or tool results rather than appearing as a separate notification. Project files show configuration and artifacts; a trace shows whether a hook actually started.

🙈 Sent to the agent

Usually context or tool output

  • memory-search — relevant memory before a supported edit or command.
  • reflection — warnings alongside the edit result.
  • Claude merge reminder — a prompt to review lessons in a later interaction.

👀 Available on disk

Configuration and outputs you can inspect

  • .claude/memory/*.json — project configuration, not proof that hooks ran.
  • .claude/memory/_pending/*.md — drafts to review with /memory-update.
  • .claude/.cache/reflect.log — automatic retrospective job log, when enabled.
To produce automatic drafts in Claude, set export HARNESS_AUTO_REFLECT=1 before launching the session. An eligible merge can then create drafts, if there are lessons to extract and the job succeeds. Otherwise, use /feedback-review and /memory-update interactively.

Check whether a hook started

A quiet hook may have run without finding a match, or may not have run at all. Enable tracing to distinguish them:

export HARNESS_HOOK_TRACE=/tmp/hook-trace.jsonl   # before launching Claude or Codex
# Run one shell command and one file edit in the session.
cat /tmp/hook-trace.jsonl

Each hook records a line at entry: hook name, event, and time. Command text and file contents are omitted. With no environment variable, tracing does nothing. Missing entries indicate that the hook did not reach its trace point; also check the trace path and hook trust if the entire file is absent.

Why trace before matching? Recording only when a hook injects content would make “ran without a match” look identical to “never ran.” Entry tracing separates those cases.

Architecture Decision Records (ADRs)

The loop can preserve both lessons and why a decision was made. An ADR records the rationale, alternatives, consequences, and evidence that code alone rarely explains.

⏩ Future work — retrospective drafts

When enabled in Claude, automatic retrospectives can write ADR drafts to _pending/decisions/. Decision chains and supersession links are proposals until a human confirms them with /memory-update.

⏪ Past work — commit-message mining

The manual mine.py script extracts decisions from commit messages in a specified revision range. It instructs the LLM to skip commits without documented rationale. This limited implementation ships with Claude; broader PR, issue, and transcript mining remains design work.

Both use the same promotion path: _pending/decisions/ → human review with /memory-update → .claude/memory/decisions/. The ADR schema is included in the memory-update skill in both adapters, so an older project template does not have to supply it. See decision mining and its current limits.

ADR gate: both Alternatives and Consequence must appear. During /memory-update review, a draft missing either is treated as ordinary memory or discarded, rather than promoted as an ADR.

Handoff

Resume work across sessions, machines, tools, and people

Handoff commands

CommandWhen to use itWhat it does
/handoff-saveBefore ending a session or switching tools, machines, or peopleSaves work state to a committable file and collects git facts. The script does not commit or push it.
/handoff-loadWhen resuming workReads a handoff and compares it with current git state.
/fwAfter switching tools without savingRecovers context from the opposite tool's local session logs.
/fw-bothWhen work spans Claude and CodexReads both sets of logs to reconstruct the combined context.
/historyWhen you need to find the right sessionLists and searches logs, then prints a fw --session command for the selected log.
Handoff versus /fw: an explicitly saved handoff becomes the portable record once committed and pushed. /fw is the local recovery path when you did not save. All recovery paths prioritize current git state over historical records.
/history finds; /fw resumes. History is read-only and does not restore work. It shows times, tools, paths, and recent user input. Use --no-content to show only metadata and paths.

/fw defaults to the opposite tool. /fw-both supplies the current tool identity so recovery can exclude that tool's live session without discarding the opposite tool's latest work.

Session AWorking now → /handoff-save "one-line summary"
▼  git commit · push  (.claude/handoff/<branch>.md; git facts collected automatically)
Session BPull on another machine or switch tools, then use /handoff-load
Known limitation in 0.12.2: saving does not commit or push, and the reported commit state covers a local commit only — push state is not checked, so confirm it separately before relying on a handoff elsewhere. Save and load now report the file's state at the time they run, which closes the mislabeling in #133. Loading still does not automatically retire the consumed handoff (#138).

What gets recorded

The portable records are ordinary Markdown files. These are the main types:

📋 Handoff — .claude/handoff/<branch>.md

Current work state, with branch, commit, and changed files collected automatically. The outline below describes the fields, which the scripts generate in English.

# Work handoff — main
## Summary       One or two lines about the task
## Done          Work already finished
## Remaining / next actions
                 Next actions for whoever resumes
## Verification status
                 Test and build results
## Git facts     Branch, commit, changed files (automatic)

🧠 Shared memory — .claude/memory/*.md

Durable rules and decisions, promoted after human review.

---
name: engine-data-separation
description: One-line summary shown in the index
type: feedback | project | reference
---
Core lesson + Why + How to apply

📝 Retrospective drafts — .claude/memory/_pending/*.md

Candidates produced by retrospective drafting, waiting for human review with /memory-update.

Rejected drafts are recorded in _rejected.md to discourage repeat proposals. It is not a permanent ban list: new evidence can justify another proposal that explains what changed.

Before choosing a memory location, classify its lifetime

/memory-update separates durable knowledge from temporary work state and facts that can be queried again.

Durable knowledge

Recurring mistakes, non-obvious patterns, rationale, stable contracts

Human review → memory

Transition state

WIP, active PRs, next actions, resume checkpoints

Suggest a handoff when actually changing sessions, tools, machines, or people

Queryable facts

Line counts, test counts, open PR status, current branch and commit

Read code, git, or command output again instead of persisting them

Status goes stale; evidence links can endure. PR #123 can identify evidence for a decision. PR #123 awaiting merge is temporary state and should not become memory. Pending drafts must pass the same lifetime check.

Resuming on another machine

Transfer the committed files; local conversation logs are not part of that transfer.

❌ Stays local

Not carried by the handoff workflow

  • Conversation logs (.jsonl).
  • Temporary caches (.claude/.cache/).

✅ Travels through git

Available after commit, push, and clone or pull

  • Handoffs (.claude/handoff/*.md).
  • Approved shared memory (.claude/memory/*.md).

Machine A: /handoff-save → commit → push. Machine B: pull → /handoff-load → compare the record with current git before continuing.

Switching tools (Codex ↔ Claude Code)

  • Shared formats — both tools read the same Markdown handoffs and memory.
  • Consistent skill names — /handoff-save and /memory-update, for example, have counterparts in both adapters.
  • One source — build.sh generates both adapters from core/.
  • Both transcript formats — the retrospective engine can read Claude and Codex logs. This input support does not mean the background job ships in both adapters; it currently ships only with Claude.
Example: work in Codex, save and commit a handoff, then load it in Claude Code. Check the current repository facts and continue from the saved context.

Installation and structure

How to install it and how the repository is organized

Install

Claude Code:

/plugin marketplace add foxyberry/agent-harness
/plugin install agent-harness@foxyberry

Codex (seven skills in 0.12.2, four hooks; merge detection and queueing only):

codex plugin marketplace add foxyberry/agent-harness
codex plugin add agent-harness@foxyberry
# Or register a local checkout: codex plugin marketplace add ./
The public marketplace installs over HTTPS without private repository access or SSH credentials.
⚠️ Codex hooks require trust. Untrusted hooks are skipped silently. Review and trust them in the post-install review screen; /hooks lets you revisit that choice. Skills remain usable without trusting hooks. Changed hook content in a later version requires renewed review.

For either tool, selectively copy and adapt project-template/: the project instructions and example .claude/memory/ data are an optional opinion pack. From the release after 0.12.2, the plugins ship a read-only copy of that .claude/memory/ part, used by /template-check.

Updates: the documented Codex CLI flow uses marketplace upgrade, then plugin remove and plugin add to refresh the installed cache. Update for a new release, not for every local development change. See README installation and update commands.

⚠️ Close Codex sessions before updating. Installing a new version can delete the old cache directory. Sessions pointing at it may lose access to their installed skills; before the 0.8.1 shell guard, missing hook scripts could also block shell commands. Restarting refreshes the paths without removing your files, commits, or conversation logs. Claude keeps old version directories.
