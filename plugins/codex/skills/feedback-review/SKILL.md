# Branch feedback review (feedback-review)

After finishing branch work, summarize the user's feedback and corrections from this session. Consider whether rules or skills could prevent the same mistakes.

## Review scope

$ARGUMENTS

## Procedure

### 1. Collect feedback

Find the user's corrections and requests in this session:
- "Don't do that," "Instead of that," or "Why did you do that?"
- "Please do this" or "Wouldn't this be better?"
- Code-change requests, especially simplification and deletion.
- Explicit requests to add a rule.

### 1.3 Collect pending drafts (`_pending`)

Read drafts **recursively**, including subdirectories, under `$CLAUDE_PROJECT_DIR/.claude/memory/_pending/`.
These may have been generated by retrospective jobs for earlier merges. Combine them with this session's feedback into **one candidate pool**.

Skip this step if there are none; automatic retrospectives are off by default, so the directory is often empty.

### 1.4 Import past sessions — **only those selected by the user**

Default to **this session**. Relevant work may be in another session or tool: if Codex implemented a change and Claude only reviewed it, Claude's log may contain little user feedback.

**Do not import past sessions automatically.** Including every recent session mixes unrelated feedback into future rules. Import only sessions **selected by the user**.

If the user wants to review past work, or this session has little material, show a list and ask the user to select:

```bash
python3 scripts/handoff.py history --from both --since 7d --limit 10 --project-dir "<absolute-path-to-user-project>"
```
> Paths under `scripts/` are relative to **the skill directory containing this SKILL.md**. Run the commands from that directory. Replace the `--project-dir` value with **the absolute path of the user project you are working on**. The skill may be in a plugin cache outside that repository; omitting this argument can select the wrong project.

- Discovery targets this project's Claude and Codex sessions, including worktrees. Check the reported matches; matching is best effort. Adjust the time window and count as needed.
- Add `--grep <keyword>` to find a topic.
- **Exclude the current session from the candidates** to avoid repeatedly reviewing this invocation.

Compact and read each selected path. Raw logs may be several megabytes; the compacted output retains user utterances in full:

```bash
python3 scripts/compact_transcript.py <selected-session-path> --require-attributed-user
```

For multiple selections, run the command for each and **label which session each candidate came from**.
If the compactor refuses retrospective input because no reliably attributed user turn exists, exclude that session. Do not use unattributed user turns to justify promoting rules or skills. Missing some old feedback is preferable to mistaking injected rules for user feedback.

### 1.45 Filter already-handled candidates

Past sessions can reintroduce lessons that were already promoted or rejected. Check three sources:

| Evidence | Location | Action |
|---|---|---|
| Already promoted | `.claude/memory/*.md` and the personal tier | Propose strengthening the existing file rather than creating another |
| Already rejected | `.claude/memory/_rejected.md` | Exclude the candidate; skip this check if the file is absent |
| Being handled now | Other candidates in this run | Merge into one candidate |

`_rejected.md` is **not a ban list**. If repetition has made a lesson worth keeping, propose it again and explain **what changed**, such as additional occurrences or their cost, so the user can decide.

### 2. Classify feedback

| Type | Description | Examples |
|---|---|---|
| Code quality | Complexity, duplication, unused code | "Simplify this," "Remove unused code" |
| Process | Workflow, approval procedure | "Ask before committing" |
| Naming | Variable and function names | "That name doesn't fit" |
| Design | Architecture and patterns | "This separation is unnecessary" |

### 3. Consider prevention

For each item:
1. **Does a rule already exist?** Check `AGENTS.md`.
2. **Could an existing skill prevent it?** Check installed skills.
3. **Is a new rule or skill needed?**

### 4. Propose additions

Propose adding a rule to `AGENTS.md`, creating a skill, or updating an existing skill.

## Constraints

- Not every comment needs a rule; distinguish one-off requests from recurring problems.
- Prefer general principles over overly specific rules.
- Do not modify `AGENTS.md` or skills without user approval.
- Use [[memory-update]] to persist feedback selected for promotion as memory.
- Include **`[skip reflect]`** in commit messages for promoted retrospective results. Otherwise the resulting PR can trigger another retrospective. This is the fallback when path-based skip rules miss the change (#130).
