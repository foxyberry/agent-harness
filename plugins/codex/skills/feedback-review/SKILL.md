# 브랜치 작업 피드백 리뷰 (feedback-review)

브랜치 작업이 끝난 후, 이번 세션에서 사용자가 준 피드백/지적사항을 정리하고 향후 같은 실수를 방지할 수 있도록 규칙이나 skill로 추가할지 검토합니다.

## 검토 대상

$ARGUMENTS

## 수행 순서

### 1. 피드백 수집

이번 세션에서 사용자가 지적한 내용들을 찾습니다:
- "~하지 마", "~하지 말고", "왜 ~했어?"
- "~해줘", "~하는게 낫지 않아?"
- 코드 수정 요청 (특히 단순화, 삭제 요청)
- 명시적인 규칙 추가 요청

### 1.3 대기 초안(`_pending`) 수집

`$CLAUDE_PROJECT_DIR/.claude/memory/_pending/` 아래 초안을 **재귀로** 읽는다(하위 디렉토리 포함).
회고 잡이 과거 머지에서 미리 만들어 둔 것들이라, 이번 세션 발화와 **하나의 후보 풀로 합친다**.

없으면 그냥 넘어간다(자동 회고는 기본 꺼짐이라 대개 비어 있다).

### 1.4 과거 세션 끌어오기 — **사람이 고른 것만**

기본은 **이번 세션**이다. 그런데 회고할 작업이 다른 세션·다른 툴에 있는 경우가 흔하다 —
Codex 가 구현하고 Claude 가 리뷰만 했으면 Claude 로그에 사용자 발화가 거의 없다.

⚠️ **자동으로 끌어오지 않는다.** "최근 세션 전부"를 후보에 넣으면 무관한 작업의 피드백이
섞이고, 그건 잘못된 규칙으로 굳는다. 후보는 **사용자가 고른 것만** 들어간다.

사용자가 과거 작업까지 보길 원하거나, 이번 세션에 재료가 거의 없으면 목록을 보여주고 묻는다:

```
python3 scripts/handoff.py history --from both --since 7d --limit 10 --project-dir "<지금 작업 중인 사용자 프로젝트 절대경로>" 
```
> ⚠️ 위 명령의 `scripts/handoff.py` 는 **이 SKILL.md 가 있는 스킬 디렉토리 기준 상대경로**다. 그 스킬 폴더로 cd 해서 실행하되, 위 예시의 `--project-dir` 를 **지금 작업 중인 사용자 프로젝트의 실제 절대경로로 바꿔서** 넘겨라 — 스킬 폴더는 플러그인 캐시라 사용자 repo 밖일 수 있어, 이 인자 없이는 git 루트 탐지가 빗나가 핸드오프가 엉뚱한 위치에 저장된다.

- 이 프로젝트에 속한 Claude·Codex 세션만 나온다(worktree 포함). 기간·개수는 조절한다.
- 특정 주제를 찾을 땐 `--grep <키워드>` 를 붙인다.
- **지금 이 세션은 후보에서 뺀다** — 자기가 자기를 회고 재료로 쓰면 같은 얘기가 맴돈다.

사용자가 고른 경로를 압축해서 읽는다(원본은 수 MB, 압축본은 사용자 발화를 통째로 남긴다):

```
python3 scripts/compact_transcript.py <고른 세션 경로>
```

여러 개를 고르면 각각 돌리고, **어느 세션에서 나온 후보인지 표시**해서 제시한다.

### 1.45 이미 처리한 것 거르기

과거 세션을 끌어오면 **이미 승격했거나 이미 버린 교훈이 다시 올라온다.** 세 곳을 본다:

| 근거 | 어디 | 처리 |
|---|---|---|
| 이미 승격됨 | `.claude/memory/*.md` 와 개인 tier | 새로 만들지 말고 기존 파일 보강 후보로 |
| 이미 버림 | `.claude/memory/_rejected.md` | 후보에서 뺀다 (없으면 그냥 넘어감) |
| 이번에 처리 | 같은 실행 안의 다른 후보 | 하나로 병합 |

`_rejected.md` 는 **금지 목록이 아니다.** 같은 일이 반복돼 값어치가 생겼으면 다시 올리되,
**무엇이 달라졌는지**(몇 번 더 반복됐는지, 어떤 비용이 났는지)를 적어 사용자가 판단하게 한다.

### 2. 피드백 분류

| 유형 | 설명 | 예시 |
|------|------|------|
| 코드 품질 | 복잡성, 중복, 미사용 코드 | "단순화해", "안쓰는 코드 지워" |
| 프로세스 | 작업 흐름, 승인 절차 | "커밋 전에 물어봐" |
| 네이밍 | 변수명, 함수명 | "이름이 적절하지 않아" |
| 설계 | 아키텍처, 패턴 | "이렇게 분리할 필요 없어" |

### 3. 방지책 검토

각 피드백에 대해:
1. **이미 규칙이 있는가?** — `AGENTS.md` 확인
2. **기존 skill로 방지 가능한가?** — 설치된 skill 목록 확인
3. **새 규칙/skill이 필요한가?**

### 4. 추가 제안

사용자에게 다음을 제안합니다:
- `AGENTS.md` 에 규칙 추가
- 새 skill 생성
- 기존 skill 수정

## 출력 형식

```markdown
## 피드백 리뷰 결과

### 이번 세션 피드백 요약

| # | 피드백 내용 | 유형 | 왜 발생했나 |
|---|-------------|------|-------------|
| 1 | "..." | 코드 품질 | ... |
| 2 | "..." | 프로세스 | ... |

---

### 방지책 분석

#### 이미 규칙이 있는 것
- (해당 규칙 인용)

#### 새로 추가가 필요한 것

| 피드백 | 제안 | 추가 위치 |
|--------|------|-----------|
| "..." | 규칙: ... | AGENTS.md > Code Quality Rules |
| "..." | skill: ... | 새 skill |

---

### 추가할 내용 (승인 필요)

**AGENTS.md 추가:**
(추가할 내용)

**새 skill 생성:** (필요시)
- 이름: ...
- 용도: ...
```

## 주의사항

- 모든 피드백이 규칙화할 필요는 없음 (일회성 vs 반복 가능성 판단)
- 너무 구체적인 규칙보다는 일반화된 원칙 선호
- 사용자 승인 없이 `AGENTS.md` 나 skill 수정 금지
- 승격 대상 피드백은 [[memory-update]] 로 메모리에 영속화하는 것과 연계
