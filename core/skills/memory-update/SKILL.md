# Memory update (memory-update)

Review lessons from this session together with pending drafts (`_pending`) generated by retrospective jobs for earlier merges, and persist the approved lessons as memory.

{{PROJECT_ROOT_NOTE}}

## Memory update procedure

### 1. Read the current MEMORY.md

Read `MEMORY.md` in the Claude auto-memory directory:
`~/.claude/projects/<encoded-project-path>/memory/MEMORY.md`, where `<encoded-project-path>` is
`{{PROJECT_ROOT}}` with every `/` replaced by `-`. When system memory instructions give an exact
path, use it **only if it belongs to this target project** — a path carried in from a session for a
different project would attach that project's personal memory to this one; otherwise fall back to the
encoded path above. This directory is outside the project; do not anchor it on `{{PROJECT_ROOT}}`,
and never encode the current working directory, which may be a plugin cache.

### 1.5 Collect pending drafts — prepared by retrospective jobs

Read all drafts **recursively**, including subdirectories, under `{{PROJECT_ROOT}}/.claude/memory/_pending/`:
- `{{PROJECT_ROOT}}/.claude/memory/_pending/*.md`: lesson drafts (`type: feedback|project|user|reference`).
- `{{PROJECT_ROOT}}/.claude/memory/_pending/decisions/*.md`: **ADR drafts** (`type: decision`); see **section 1.6** for promotion.
These may have accumulated from **multiple earlier merges**, not just this session.

- Combine these drafts with the items extracted in step 2 into **one candidate pool and deduplicate together**.
- Deduplicate by meaning: (a) merge candidates on the same topic; (b) strengthen an existing MEMORY.md entry or memory file instead of creating a duplicate; (c) if a lesson was already rejected in **`{{PROJECT_ROOT}}/.claude/memory/_rejected.md`**, **exclude it from the candidates**.
  - Different wording does not make it a new lesson; the user already decided not to retain it.
  - This is **not a ban list**. If repeated occurrences have made the lesson worth keeping, propose it again and explain **what changed**, including additional occurrences or their cost, so the user can decide.
- Apply the **lifetime classification in section 2.4 before deciding promotion**. Propose discarding work state and reconstructible values; do not promote or merge them.
- Give each candidate a proposed outcome: **promote / merge / discard**. Present a brief list to the user and obtain their decision.
- **Delete processed drafts** from `{{PROJECT_ROOT}}/.claude/memory/_pending/` and `{{PROJECT_ROOT}}/.claude/memory/_pending/decisions/`, whether promoted or discarded. Leave undecided drafts in place.
- **Append one line for each discarded candidate to `{{PROJECT_ROOT}}/.claude/memory/_rejected.md`**, creating the file if needed. Deleting a draft alone loses the rejection history, so another session can recreate it from the same transcript (#109).

  ```markdown
  # Rejected retrospective drafts

  Candidates that `/memory-update` decided not to retain. Retrospective jobs and this skill consult this list to avoid recreating them. This is **not a ban list**: repeated occurrences may justify proposing a lesson again.

  - `slug-name` — One-line reason for discarding it (YYYY-MM-DD).
  ```

  - This file is **append-only**. Do not delete or rewrite entries; older entries eventually fall outside the consumer's read limit.
  - Always give a reason. "Too minor" and "Already in AGENTS.md" imply different decisions on later review.
  - **Do not commit it**; the template ignores it by default. Rejected lessons expose **working habits and mistake history**, so they belong to the personal tier. Committing them to a public repository would publish them worldwide.
    - Claude and Codex read the **same path within this project**, so both tools can use it without a commit. It does not travel to **another machine**.
    - Reasons must describe **the candidate, not the person**: "too minor," "duplicates AGENTS.md," or "unclear generalization" is sufficient.
    - If an item deserves team sharing, such as a decision to put guidance in `AGENTS.md` instead of memory, promote it through a **proper shared memory or rules document**. Do not use this file for sharing.

### 1.6 Promote decision (ADR) drafts — `{{PROJECT_ROOT}}/.claude/memory/_pending/decisions/`

Handle `type: decision` drafts separately from lessons. **The canonical schema is defined below**. If a project has `{{PROJECT_ROOT}}/.claude/memory/decisions/README.md`, that file is a human-readable guide, not the canonical schema. Projects copied from an older template may lack it entirely; promotion must still work.

Each ADR contains exactly one decision. Split drafts containing multiple decisions before promotion, and confirm each `chain`. Link deliverables through `artifacts` rather than pasting them into the body.

**Frontmatter**

```yaml
---
name: <slug>                # Must match the filename stem.
description: <one-line-summary> # Required; used by INDEX and search summaries.
type: decision
id: adr-YYYYMMDD-NNN        # Assigned on promotion; immutable link target.
chain: <chain-slug>         # Topic; supersedes links must stay within one chain.
status: active             # Stored values: active | rejected only.
supersedes: [<id>, ...]     # One-way links; derive superseded_by when reading.
keywords: [<term>, ...]     # Required search terms.
commit: <sha>              # Commit enacting the decision; omit if unavailable.
artifacts:                 # Optional deliverable links; do not paste into the body.
  - path: <path>
---
```

**Required body sections**

```markdown
## Context
Situation and constraints that required this decision.
## Decision
What was decided, in one or two lines.
## Alternatives
Options considered but not selected, and why. Required.
## Consequence
Results and effects, including benefits and accepted costs. Required.
## Evidence
Supporting session, commit, PR, and issue links.
```

`supersedes` is one-way because bidirectional links require rewriting old files and can leave an inconsistent graph when only one edit succeeds. Appending new links is safer. Links use an **ID**, not a content hash, so legitimate edits do not break the chain.

1. **Check the ADR gate**: both `## Alternatives` (unselected options) and `## Consequence` (results) must exist. Otherwise, do not promote it as an ADR; consider ordinary memory or discard it.
2. **`proposed_*` fields are proposals; the user confirms them**. Present `proposed_chain`, `proposed_supersedes`, and `confidence` for a decision:
   - **Chain**: **"Continue existing chain `<slug>` / create chain `new:<name>` / discard."** Every ADR has **exactly one `chain`**. An independent decision gets a new chain; there is no unassigned state. Incorrect lineage is the worst failure here, so never confirm it automatically.
   - **Supersession**: if it replaces an earlier decision, put that decision's `id` in `supersedes`; otherwise use `supersedes: []`. This is separate from chain assignment.
3. **Convert to confirmed frontmatter** and save to `{{PROJECT_ROOT}}/.claude/memory/decisions/<name>.md`:
   - **Filename: `<name>.md`**, using a descriptive kebab-case slug and retaining or refining the draft's name. The `id` is a **separate frontmatter field**: the filename is readable, while the ID is a stable key for links and `supersedes`.
   - **Assign** `id: adr-YYYYMMDD-NNN`, using the next sequence number for that date. Once assigned, it is immutable.
   - Write scalar fields and list values such as `keywords: [a, b]` on **one line**; the index parser reads line by line. The optional `artifacts` block follows the schema above.
   - Convert `proposed_chain` to `chain` and `proposed_supersedes` to `supersedes`. Keep links **one-way**: never store `superseded_by`; derive it when reading. Add `status: active` and remove `confidence` and all `proposed_*` fields.
   - Require a one-line `description` for INDEX and search summaries. Preserve it if present; otherwise derive one from `name` and Context.
   - Require useful `keywords`; improve weak ones to support retrieval.
4. **Apply one-way supersession**: if this ADR replaces an existing decision, put the old ID only in the new file's `supersedes`. **Do not edit the old file**. At read time, an ID referenced by another ADR's `supersedes` is treated as superseded, avoiding edits and conflicts in older files.
5. **Register in INDEX**: add `[<id>](decisions/<name>.md) — [chain: <chain>] <one-line-summary>` to the ADR section in `{{PROJECT_ROOT}}/.claude/memory/INDEX.md`. The link target stays relative to that INDEX. Reuse an existing ADR section, including one whose heading is still in the project's original language. If absent (first ADR or older INDEX), append `## Decision records (ADR)` and the entry.
6. Delete processed drafts from `{{PROJECT_ROOT}}/.claude/memory/_pending/decisions/`. These are **shared-tier records and require a commit through a branch and PR**.

Discarded drafts are recorded in `{{PROJECT_ROOT}}/.claude/memory/_rejected.md` for retrospective jobs and this skill to consult. Draft generators preserve existing files by adding numeric suffixes when slugs collide; they do not deduplicate equivalent content. Merge or reject duplicate proposals during review.

### 2. Extract candidates from this session and combine them with pending drafts

**feedback (corrections and confirmed useful patterns)**
- User corrections such as "Why?", "Don't do that," "That's wrong," or "That was a mistake."
- Behavior that must not recur.
- Non-obvious patterns confirmed with "Yes," "Good," or "Do it that way."

**project (changes in project knowledge)**
- Non-obvious behavior or contracts established by a merge, and why they exist.
- Changes to significant design decisions.
- API constraints or interpretations that are hard to infer from code alone.

**reference (new external resources)**
- New documentation, dashboards, channels, and similar resources.

### 2.4 Classify lifetime before choosing where to save

Classify every candidate before considering scope:

| Classification | Examples | Action |
|---|---|---|
| **Durable knowledge** | Recurring mistakes, non-obvious patterns, design rationale, stable contracts | Choose a storage tier in section 2.5 |
| **Work state for a transition** | Resume checkpoints, WIP, ongoing PRs, next actions | Do not save in memory. Suggest `/handoff-save` only when **actually** switching sessions, tools, machines, or people |
| **Reconstructible values** | Line counts, test counts, open PR status, current branch or commit | Do not save. Point to the command or canonical source when needed |

- A handoff is not a general state store. It is a file intended for committing to pass current work during a transition; do not create one or move material into it automatically.
- PR and issue numbers can be evidence and stable identifiers. Changing status such as "PR #123 awaiting merge" is not durable knowledge.
- Do not store current API structures or metrics that can be reconstructed directly from code or dashboards. Retain only lasting contracts, interpretations, and caveats.
- If a pending draft or existing memory contains work state or reconstructible values, propose discarding it rather than promoting or merging it.

### 2.4.1 Check sensitive information before promotion

Check every candidate and pending draft for API keys, tokens, passwords, cookies, personal identifiers, private URLs, and other sensitive information.

- Never save sensitive values in either the personal or shared tier.
- If the lesson is useful, remove secrets completely or generalize it, then review again.
- Propose discarding anything that cannot be generalized safely.
- Delete processed pending originals according to the user's approved outcome. Never copy secrets into completion reports or PR descriptions.

### 2.5 Classify scope and route to the personal or project tier

Determine storage by **scope, separately from type**:

| Type | Scope | Storage tier |
|---|---|---|
| user | Personal | Personal |
| reference / project | Project | Shared |
| **feedback** | **Case by case** | See below |

**Feedback scope:**
- **Personal preferences** about tone, style, or working with this user, such as "Lead with a short conclusion" or "I dislike this approach": personal.
- **Project rules** for the codebase or team, such as "No direct push to main," "Kotlin javaParameters is required," or Spring DI conventions: shared.
- **If ambiguous**, ask whether it is a personal preference or a project rule; let the user choose personal, project, or neither.

**Storage locations:**
- **Personal**: `~/.claude/projects/<encoded-project-path>/memory/<name>.md` and its `MEMORY.md` index. This is per-machine and outside Git; use the same directory read in step 1 so later sessions can load it.
{{PERSONAL_TIER_NOTE}}
- **Shared (project)**: choose by purpose:
  - Mandatory rules that must always be followed: the appropriate section of **`{{PROJECT_ROOT}}/{{RULES_FILE}}`**.
  - Reference facts, patterns, and design decisions: **`{{PROJECT_ROOT}}/.claude/memory/<name>.md`**, with frontmatter; the [[memory-search]] hook exposes relevant entries before edits and writes.

Shared-tier changes **require a commit through a branch and PR, never directly on main**. Personal-tier changes under `~/.claude` do not. State "Shared changes require a commit/PR" in the completion report.

For retrospective-result PRs, include **`[skip reflect]`** in commit messages. Path-based skip rules are the first filter, but mixed rules and supporting files have escaped them (#130). The marker provides a fallback independent of file paths and prevents another retrospective being requested for the retrospective's own output.

### 3. Storage rules

**Check for duplicates**: update existing files instead of creating duplicate entries.

**Keep:**
- Recurring mistakes, non-obvious patterns, and design rationale.
- Stable contracts, interpretations, and caveats that are hard to infer from code.

**Do not keep:**
- Resume checkpoints, WIP, ongoing PRs, or next actions.
- Changing or reconstructible current values such as line counts, test counts, and open PR status.
- Facts available directly from code or `git log`/`git blame`.

### 4. File format

```markdown
---
name: memory-name
description: One-line description for the MEMORY.md index.
type: feedback | project | reference | user
---

Content. For feedback/project entries, include **Why:** and **How to apply:**.
```
